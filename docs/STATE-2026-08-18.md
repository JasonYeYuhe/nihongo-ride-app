**`roastmate-signing.keychain-db` was an abandoned keychain still in the search list, and it
broke the macOS App Store export.** RESOLVED 2026-08-23; the full causal chain, because the
global runbook pointed the other way:

1. It was a hand-built temporary signing keychain for RoastMate's OLD macOS `.pkg` path. That
   path was abandoned — `RoastMate/scripts/build-upload-asc.sh`'s own header records the
   decision: passing the ASC API key with `-allowProvisioningUpdates` "lets Xcode fetch/manage
   the distribution + Mac-Installer certs itself … So neither the temp keychain nor altool is
   needed."
2. Nobody removed it from `security list-keychains`, and it held the ONLY
   `3rd Party Mac Developer Installer` identity in the list.
3. `productbuild` searches the whole list, found that identity, and used it — so Xcode's
   automatic signing never fetched one of its own.
4. That keychain would not authorise this session, so signing the `.pkg` failed `-60008`.

The fix was one line, and the export succeeded first try afterwards:

    security list-keychains -d user -s ~/Library/Keychains/login.keychain-db

(The user domain needs only `login.keychain-db`; `System.keychain` comes from the system domain.
Adding it explicitly is what produces the duplicate `System.keychain` the runbook calls
cosmetic — it is this command, run without de-duplicating.)

`~/.claude/CLAUDE.md` still says that keychain is "unrelated — don't chase it … contains no
codesigning identities … irrelevant to Apple signing here". True of `codesign`, false of
`productbuild`, and it cost a day. **The global note needs correcting.**

Two diagnoses were wrong on the way, both recorded because the pattern matters more than the
verdicts. The first blamed the screen lock — `IOConsoleLocked` was true, it matched a documented
trap, and the investigation stopped there. The second over-corrected and said the lock was
irrelevant. Both were half right and neither was the cause: the identity was in the wrong
keychain the whole time, and the lock only explained why that keychain would not open.

**The macOS App Store export signs a `.pkg`; the archive only runs `codesign`.** That is why
an archive can succeed while the export fails, and why iOS is unaffected — it ships no `.pkg`. v1.25's upload
failed with `exportArchive productbuild failed`, and the distribution log gives the real cause:

    productbuild SignData failed: NSOSStatusErrorDomain Code=-60008
    "Unable to obtain authorization for this operation."

The certificate was present (`3rd Party Mac Developer Installer`), `login.keychain-db` was
unlocked and `no-timeout`, and `ioreg -n Root -d1 -a | grep -A1 IOConsoleLocked` said `<true/>`.
The macOS App Store path wraps the `.app` in a signed `.pkg`, and THAT signature cannot be
authorised while the console is locked — the archive step, which only runs `codesign`, had
already succeeded. iOS is unaffected because it ships no `.pkg`.

The global CLAUDE.md table says `codesign` survives screen lock and `notarytool` does not; this
is a third row: **`productbuild` does not**.

### The floor: 224 entries no sentence can teach (one was appealed and won)

`docs/measurements/entries-no-sentence-can-teach.json`. Three kinds:

- **98** teach a minority reading whose common counterpart has its own entry — 鼠 ねず beside
  ねずみ, 火傷 かしょう beside やけど. **92 of those siblings already ship a sentence**, so the
  word is taught, just not by that card.
- **118** teach a reading that differs from the default for the spelling, with no sibling.
- **9** failed two independent generation rounds for the identical stated reason. Three of
  those are headwords that are **not valid Japanese spellings**: 擽ぐったい duplicates the stem
  of 擽ったい, 引受る cannot yield ひきうける (needs 引き受ける), ぺん is a loanword in hiragana
  where only ペン occurs.

The rule that ended the retry loop: an entry failing two independent rounds with the same
defect is blocked, not unlucky. Regenerating cannot help, because the generator and the
reading gate share the assumption these entries violate — that a spelling has one likely
reading — so the failure is invisible from inside the pipeline.

**The rule survived an appeal in v1.22 and came out narrower.** v1.21 §A produced a SECOND
parser — Apple's Japanese speech front-end, a different implementation that can be asked
decisively — so "the pipeline cannot judge itself" stopped being the end of the argument.
Six entries got a hearing (`scripts/check_forces_reading.py`,
`docs/measurements/v122-blocked-entry-rescue.json`): **one was rescued** (未だ/いまだ, because
未だに is a fixed form that excludes まだ grammatically — *まだに is not a word), one looked
rescued and was not (違える: the audio proved the reading, but the sentence used 寝違える, a
different verb that merely contains the headword), and four stayed blocked — two of them now
on two parsers disagreeing rather than one tool's verdict.

So the rule is a shipping gate, not a claim about the language, and an appeal now costs one
script run. The other 216 were NOT retried: their blocking reason is the structural one, and
the rescue worked for a grammatical reason peculiar to that entry.

**Decided in v1.21 §C.** They keep their readings. Codex and Gemini were asked again and both
said retire; both argued that the card asks "given this spelling, what reading?" and these
leave it underdetermined. The app never asks that — every mode prints the reading beside the
spelling, so the learner types what they can see. 87 of them gained a note naming the everyday
reading of their spelling and the card that teaches it; the other kind of note was built and
cut for having no second source. Three headwords were resolved as data: ぺん retired toward the
N5 ペン it duplicated, 擽ぐったい and 引受る corrected in `surface` only (`kana` frozen, so the
SM-2 answer never moved).

In-place `kana` edits remain refused, for the original reason: `SRSCard.id` IS `VocabEntry.id`,
so editing kana preserves a learner's schedule while silently swapping the answer being tested.
`check_vocab_diff.py` freezes `kana`, and now refuses a manifest-declared `surface` fix that
tries to move `kana` alongside it.

**A live bug came out of checking whether a retirement was safe.** `resolves:` — the filter that
stops a retired entry counting toward work that no longer exists — was wired into ONE of the
five places that count due cards. The badge, the widget, the reminder body and the journal
forecast counted every stored card, so the two entries v1.18 retired have been inflating them
ever since for anyone who studied them. Fixed in v1.21 §C, with a test on each call site.

## The pipeline

    scripts/gen_batch.py            generate (agy → gemini-3.6-flash), declares a sense per sentence
    scripts/pilot_gate.py           deterministic gates; three-way survive / vocabularyGap / reject
    scripts/make_review_chunks.py   interleaves survivors and gaps, WITHHOLDS the routing verdict
    scripts/apply_batch.py          merge, requires --approved, carries the sense into exMeta
    scripts/gen_sentence_kana.py    exKana + exTokens, with round-trip and alignment gates
    scripts/check_vocab_diff.py     identity frozen, meanings append-only, examples write-once
    scripts/check_translation_agreement.py   en/zh subject and day-part disagreement
    scripts/pipeline_status.py      where a batch stands

`check_vocab_diff` supports `--manifest`: a reviewed structural change (a removal, a rewrite,
a retirement) declares every id and field it touches, and the guard then fails on anything the
manifest did NOT predict **and** on anything it promised that did not happen. It is stricter
with a manifest, not looser.

Review shape that has held for six batches: three lenses (Japanese correctness, translation
fidelity, "would this card mislead a learner") over interleaved chunks, then a sense-triage
with 3–8 independent classifiers and an adversary whose default is to refuse.

## What v1.21 measured about the synthesizer

Kyoko is deterministic, so two texts rendering to the same WAV bytes were converted to the
same phonemes — byte-identity is PROOF of what she said, not an inference. It is decisive and
quiet: it speaks for 521 of 6,723 sentences, of which 494 match their `exKana` and **27 are
proven to say something else** (私 as わたし, 風車 as ふうしゃ, 何 as なに …). A nearest-hypothesis
pass covers the rest and scores **100% recall (27/27)**. The false-positive half of that figure — long recorded here as 0/494 — was arithmetic, not measurement, and is withdrawn: the false-positive population is BY DEFINITION the sentences whose `exJP` audio is byte-identical to an `exKana` variant, so `own = dtw(x, x)`, and the repo's own DTW returns at most 8.9e-17 for a matrix against itself against a minimum of 0.445 for distinct pairs. `best < own` is unsatisfiable; 0/494 was guaranteed before a clip was rendered. The recall half stands — those are the proven positives and the instrument found all of them. (Withdrawn in v1.25 §A.) 977 sentences (14.5%) are withheld from dictation — v1.25 §A released 27 whose recorded
complaint was repaired rather than re-decided — and they remain fully available in sentence mode.

The calibration is the part to remember, and it has TWO lessons now. The first used synthetic
decoys — a reading replaced by random kana — and put the false-positive rate at 4.7%, which made
a working
instrument look like mostly noise. Random kana are a HARDER test than real alternative
readings. Calibrating on the wrong population is its own way of getting a wrong number from a
clean-looking run.

Three lessons hold across all of them. **A fix applied to one call site is not a fix** — five
of the first eight were the same repair left half-done. **The count and the run must share a
predicate, not agree by inspection**: every one of these passed review at the time because
both sides looked right in isolation. And the cheapest detector found so far: **where a
comment states a contract, check whether anything enforces it.** Three of v1.23's six were
found exactly that way — the code had a sentence in it claiming a property nothing checked.

**#23, 2026-08-30 — and it is the first one that sat in a KILL CRITERION rather than a
displayed number.** `PLAN-STAGE1.md` §K's STOP branch read *"at least one returned counter
showing `settingsRowAppeared > 0` with `furthestBucket == kyoto`"*. But
`UnlockOfferLedger.swift` states the contract itself: the Settings row is *"the entrance, not
the offer — and the two are a screen apart, so they are counted apart"*, `offerAppeared` *"is
the event that means somebody was actually in a position to buy"*, and reading one as the
other is *"two different predicates answering one question — the shape this project has
shipped twenty-two times."* **The instrument was built correctly and the decision rule then
asked it the wrong question.** Two aggravations: `furthestBucket` is a lifetime high-water
mark, so the conjunction never said the two things happened *together* (the row could have
appeared at 400 m); and `shareableSummary` summed all eight buckets, so the quantity the
branch asked about was not printable on the one readout a customer could return. Found by
adversarial review before day 0, not after. The lesson generalises past code: **a
pre-registration is a predicate too, and nothing was checking it against the instrument.**

What is now in place against it, and what is not:

  * `VocabStore.resolvesID` is the one predicate. It replaced fifteen hand-written copies, of
    which two were the bugs above. This removes writing it DIFFERENTLY.
  * `Tests/VocabKitTests/ResolvesCallSiteTests.swift` reads the shipped source and fails if a
    learner-facing due count omits `resolves:`. This removes FORGETTING it — which is what
    actually happened both times, and cannot be caught at runtime, because a missing argument
    is indistinguishable from a store where everything resolves. It counts the calls it
    inspected and fails below ten, so a scan that reads nothing cannot report "clean".
  * **v1.24 §C made the argument required.** All ten `= { _ in true }` defaults are gone, so
    forgetting it is now a compile error rather than a silently wrong number. Production
    needed none of them — the app compiled unchanged — which was the whole argument: the
    default served only tests, and cost releases in production. Test noise is absorbed by a
    shim per test target (`Tests/*/UnfilteredForTesting.swift`), 42 call sites, none edited.
  * **The scanner now reads declarations too**, because the call-site scan had a blind spot
    that was hiding two live defects, and the compiler cannot catch a counting method that
    never declared the parameter. Any `public func`/`public var` on a `*Store` whose name
    begins due/reviewed/leech/weakest must take `resolves:`. Calibrated on the exact two it
    found, plus the false positive its first version had (`SRSCard.dueDate` — one card's own
    date, where the predicate is meaningless).
  * Neither helps a NEW promise built on a filter that has no keyword. The audit's own
    calibration named this: its rule works because the codebase adopted `resolves:` in
    response to this very defect. For the next novel one, the sweep degenerates to "read
    everything". v1.24 §A's "ride these words" is exactly such a path — no `resolves:`
    keyword at the call site — and it is held instead by a single function
    (`StumbledWords.rideableIDs`) that both the count and the run must call, with a test
    asserting the button's number against the length of the queue the button produces.

## Traps this project has already paid for

- **A discipline written in prose must say, per clause, WHICH DIMENSION it constrains — space,
  time, frequency, or population. The dimension it does not name is not "all of them by default";
  it is "nobody is checking."** Measured against a real five-clause rule rather than argued.
  Stage 1's placement discipline was handed over as: *no modal · no badge · no post-ride
  solicitation · no recurring reminder · and deliberately far from the rating prompt.* After
  v1.30 added a second entrance, the outcome per clause was:

  | clause | readings | outcome |
  |---|---|---|
  | no modal | one | held |
  | no badge | one | held |
  | no post-ride solicitation | **two** — is "post-ride" the screen, or the flow? | held **only** because "solicitation" was defined explicitly (state + neutral navigation is not solicitation) and the argument written down |
  | no recurring reminder | **two** — a prompt, or anything persistently visible? | **violated.** A menu element is seen on every menu visit; the plan had claimed "not recurring" and that claim was false |
  | far from the rating prompt | **two** — space, or time? | **the defect.** Asserted spatially; the collision was temporal |

  **Every clause with a single reading survived. Every clause with a second reading needed
  something extra**: one an explicit definition, one an honest retraction, one a code fix found
  only on review. The three that held were not better respected — they were unambiguous.

  *Where the fault actually sits, and this is the correctable part:* the v1.27 component that
  collided was not at fault — it could not have foreseen a second entrance, which is what the
  discipline existed to prevent. **The fault is in the handover, which passed an underdefined
  clause on as though it were a defined one.** "Far from" felt like a rule and was a gesture. That
  is fixable by writing; "somebody notices in time" is not.

  *The habit:* when writing or receiving a prose constraint, annotate each clause with its
  dimension before relying on it. Where a clause has two readings, either split it into two
  clauses or pick one and record the choice — an unstated second reading will be discovered by
  the first feature that happens to live in it.


- **Two components can each be correct, each green, each honestly documented, and still combine
  into a defect — because "we select the same population" is written in neither.** Found
  2026-08-30, on review, by the session that had written one of the two components.
  `ReviewPromptLedger.decide` (v1.27) gates the App Store rating prompt on `wasLogged` /
  `lifetimeRides` / `riddenDays` / `accuracy`. **Not one of those mentions distance** — and every
  one of them selects for *a long accurate ride by a rider who has come back many days*. That is
  precisely the profile of the ride that crosses 25 km into Kyōto, which is the ride v1.30's second
  purchase entrance appears on. So the app would ask for a rating and then, one tap later, reveal a
  new element opening a purchase screen: **two asks in one session, on the population most likely
  to buy.** Neither component was wrong. Neither component's tests were weak. The interaction lived
  in no file, so no single-component review could see it.
  *The check that would have caught it:* when a new element appears **conditionally**, name the
  population its trigger selects, then ask what else fires for that same population at that same
  moment. Fixed via `RideMoment.openedANewOffer`, which yields the prompt for exactly one ride —
  placed **before** the cooldown and annual-cap clauses so yielding does not spend one of Apple's
  three requests per year.

- **A rule with two dimensions gets asserted along one, and the passing test then licenses a false
  claim about the other.** Same incident, and it is the reason the collision above survived a
  review pass. The placement discipline says the offer stays *"far from the rating prompt"*.
  `PaidRouteRowTests` asserts the offer is not on the results screen — that is **space**. The
  collision is in **time**. Both readings use the same word, so PLAN-STAGE1 was written to say the
  clause was "unchanged and asserted", which was true of screens and false of sessions.
  **A green assertion and a green assertion that does not cover your question look identical**, and
  the reviewer who spots the word matching stops before checking what the assertion actually
  asserts — which is this file's oldest lesson, applied to a *reader* rather than to code.
  *The habit:* when recording that a rule is enforced, name the dimension. "Not on the same screen"
  is a claim a test can carry; "far from" is not, and collapsing the second into the first is where
  the gap opens.

- **Proving a policy yields is not proving anything sets the flag.** The first fix for the above
  proved `decide` returns the new outcome when `openedANewOffer` is true. Mutating `finishGame` to
  pass a hard-coded `false` left **the whole suite green** — guard present, nothing reaching it,
  v1.26 §B once more. Worse, the binding test's first draft passed for an unrelated reason: its
  seeded journal held two rides against a `minimumLoggedRides` of 3, so `decide` returned
  `.tooFewRides` and never reached the clause under test. **An assertion that passes for the wrong
  reason and a broken assertion are the same object.** What fixed both: a **paired control that
  must fire** — same seed shape, same ride, same policy, differing only in the variable under test.
  If the control is not asked, the experiment proved nothing.


- **Display SLEEP stalls `xcodebuild test` at the build→test handoff, and it is not the screen-lock
  trap.** Measured 2026-08-30: with the display asleep, the iOS UI suite built cleanly, touched the
  `.xctest` bundle, and then did nothing — 0% CPU, indefinitely, **four consecutive runs, always the
  same point**. `Simulator.app` never launched; `xcrun simctl` reported the device booted
  throughout, so every obvious check said the environment was fine. Wrapping the run in
  `caffeinate -d -i` was the only change, and it passed 5/5 first try.
  **The distinction is the whole value of this entry:** the console was UNLOCKED every time
  (`ioreg -n Root -d1 -a | grep -A1 IOConsoleLocked` → `false`), so this is NOT the screen-lock
  trap CLAUDE.md records for notarization. XCUITest drives a real GUI and needs a live window-server
  session. `scripts/run_ios_placement_tests.sh` and `scripts/run_store_gates.sh` now hold the
  display awake themselves, so the trap cannot recur through them.


- **Agent worktrees live INSIDE the repo and the build copies them.** Four review-agent
  worktrees under `.claude/worktrees/` totalled **1.5 GB**, one of them holding a leftover
  scratch test file, and `build-appstore*.sh`'s rsync excluded `.git`, `build`, `.build` and
  `.xcodeproj` but not `.claude` — so every release build copied all of it. Fixed by adding
  `--exclude .claude` to both scripts. Check `git worktree list` after any agent fan-out;
  removal is `git worktree remove --force` plus `git branch -D worktree-*`.
- **An agent worktree containing its own `Package.swift` does not slow `xcodebuild` down — it
  stops it.** The trap above records that these get copied into release builds (1.5 GB). That is
  the cheap half. On 2026-08-30 `xcodebuild -list -project NihongoRide.xcodeproj` **timed out at
  0% CPU**, having loaded `SwiftPM.framework` and then done nothing, and it was not a project
  change: reverting `project.yml` and regenerating reproduced it. The cause is a **second Swift
  package nested under the root package directory** — `.claude/worktrees/<id>/Package.swift` —
  which xcodebuild's SwiftPM integration stalls on. The decisive control: rsync the repo to
  `/tmp` excluding `.claude`, regenerate, and `-list` answers in seconds.

  **So a build gate must copy before it builds, rather than depend on the repo being clean.** The
  next agent fan-out will leave another one. `scripts/run_store_gates.sh` exists for that reason
  and not as a patch for one directory.

- **And this file's own cleanup instruction does not work on those worktrees.** The line above
  says removal is `git worktree remove --force` plus `git branch -D worktree-*`. **The first half
  hangs** — reproduced at 60 seconds on both `git worktree remove --force` and `git worktree
  prune`. The branch deletion is fine. What works is `rm -rf`, and it is *very* slow: files under
  `~/Documents` carry `com.apple.provenance`, so a hundred thousand small files are walked one
  xattr at a time.

  Two more things measured while diagnosing it, because both defeated the obvious checks:
  **`du -sh` reported 0B for a directory holding 77 MB**, and the `.build` inside had *today's*
  mtime — an agent had built in it, so it was not a static leftover but a growing one. And
  `git -C <worktree> status` hangs while something is building in there and answers instantly
  when nothing is: a hang is evidence about the moment, not about the directory.

- **Two ASC resources are about territories, and only one of them has territory ids.** Filtering
  by `id == "CHN"` works on the first and silently returns nothing on the second:

  | resource | id |
  |---|---|
  | `territories` (what `availableTerritories` returns) | plain — `USA`, `FRA`, `CHN` |
  | `territoryAvailabilities` | base64 of `{"s":"<app id>","t":"USA"}` |
  | `inAppPurchasePricePoints` | base64 of `{"s":"<iap id>","t":"CHN","p":"10000"}` |

  The composite ids embed the object they belong to, so **a price point id from one IAP cannot be
  reused on another** — a new product must look up its own. And a filter written against the
  plain shape produces "CHN is not in the availability list", which is **completely wrong and
  completely plausible**, and acting on it would remove a territory that was already there.

- **A new in-app purchase inherits NO territory availability, and App Store Connect does not say
  so.** The v2 handoff inferred that a new IAP would pick up the app's 175 territories. Measured
  2026-08-30: the availability resource **does not exist** on a freshly created product — the
  relationship 404s — and 175 territories had to be POSTed explicitly. Left alone the product is
  simply unpurchasable, with no error anywhere, in every territory including the one holding 48%
  of this app's installs. **A failure that reports nothing looks exactly like a success**, which
  is this project's oldest rule arriving in App Store Connect.

- **An `rsync --exclude` pattern without a leading slash matches at every level.** A build gate
  written with `--exclude 'NihongoRide-*'`, intending the stale artefacts at the repo root, also
  ate `xcode/NihongoRide-iOS.entitlements`. **It cost two minutes rather than a release only
  because xcodegen refused to generate and said why** — the same defect behind a tool that
  degrades quietly would have shipped an app with the wrong entitlements. Anchor the pattern.

- **A test target can damage the user's real data through a door the sandbox does not cover.**
  v1.24 added the first app-layer test target; every `AppModel` it built called
  `refreshWidgetSnapshot`, which writes to the **App Group container** — outside
  `supportFileURL`, and therefore outside `supportDirectoryOverride`. Seven models per
  `swift test`, each computed from an empty sandbox, each stamping fourteen days of zeros onto
  the owner's real home-screen widget. It had already happened before the review found it.
  Two lessons, and the second is the one worth keeping: the sandbox assertion was GREEN, because
  it checked the one door that was known about. The replacement asserts the property — running
  the tests changes nothing that belongs to the user — over every location, so the next escape
  trips it without anyone predicting which door it uses. There are three such locations:
  Application Support, the App Group container, and `UserDefaults`.
- **A gate validated by what it CATCHES has not been validated.** v1.25 added a rule that a
  sentence must read its own headword the way its card teaches, found 21 offenders, calibrated
  it both ways, and shipped it. It matched a single token, so the 240 entries whose headword the
  tokenizer splits were never inspected — and 26 more offenders sat behind it, ten of them N5
  counters and dates (四つ graded as よんつ, 二日 as ふたか). The question that finds this is not
  "what did it catch" but "what can it not see": for any scan, compute the population it SKIPS
  and look at a sample of it.
- **`open(path, "w")` truncates before it writes.** A script that raises between the two leaves
  an empty file; a stray `None` emptied `project.yml` during v1.25 and only version control
  saved it. Write to a temp file in the same directory and `os.replace`.
- **Chained string replaces cross their targets.** Bumping the submit script's build numbers with
  `"46"→"47"` then `"47"→"48"` gave BOTH platforms 48, because the first replace made macOS look
  like iOS. Version numbers are per-platform and getting them crossed is a rejection. Locate by
  the enclosing target or platform, never by a value another line also holds.
- **The headless renderer cannot verify accessibility text sizes, and will silently pretend it
  can.** `ImageRenderer` does not drive `@ScaledMetric`, which `scaledSystemFont` is built on —
  so injecting `dynamicTypeSize` or `sizeCategory` yields AX3 and AX5 renders that are
  byte-identical. v1.25 added such renders, looked at "AX5", found the layout fine, and only
  caught it by md5-ing the two files against each other. Large-type layout is device-verified
  (Gate E); `ScaledFont.swift` has said so since v1.7 and it is easy to walk past.
- **Measuring what a rule BLOCKS is not measuring whether it is right.** v1.24's
  `inflectionalTails` was written from intuition and validated by its effect — 12.8% of
  resolutions, 2,695 past-tense た. Two of its members occur zero times in the corpus, because
  Sudachi emits `ましょう` and `させる` rather than `ましょ` and `させ`, so the rule missed N5
  grammar entirely while its number looked convincing. Any list of surface forms is a claim
  about the data: assert every member occurs, and prefer deriving the set to writing it.
- **`Bundle.main.bundleIdentifier != nil` is not "this is the app".** Under XCTest hosting it is
  `com.apple.dt.xctest.tool`, and the App Group container still resolves. The guard works today
  only because the app tests use swift-testing, whose SwiftPM entry point reports nil. Sandbox
  the destination, do not sniff the process.


- **Adding a stored property to a struct in a library target can leave SPM's incremental
  build inconsistent, and it presents as a SIGSEGV in an unrelated test.** v1.24 added one
  field to `VocabStore`, which changed the struct's layout; object files compiled against the
  old layout were not all rebuilt, and `swift test` began crashing with signal 11 inside
  `GameSession.makeWeak` — a v1.23 test that had nothing to do with the change — with the
  crash point moving between runs and the output garbled mid-line. Every symptom points at a
  memory-safety bug in the new code. It is not one. **`rm -rf .build` and rebuild**, and only
  then start diagnosing. Confirmed by bisection: the same tree passed clean after a full
  rebuild, and 486 tests went green. Cost about an hour, most of it spent reading a crash log
  for a bug that did not exist.

- **`swift test` output is not a reliable input to a script.** With a failure present the
  runner can exit on a signal with truncated, interleaved output, so a harness that parses the
  console can see a suite as "not failing" when it never ran at all. Anything automated over
  `swift test` must assert that the test it cares about actually appeared in the run. See the
  mutation harnesses described under v1.24 §A.

- **`try!` on `#require` in a test aborts the process.** One failing app-layer test took twelve
  unrelated ones down with it and left a red build unreadable. Use a `throws` test and plain
  `try #require`, so a failure fails alone.


- **Finder/iCloud duplicate copies appear inside `Sources/` and break the build.** On
  2026-08-18, two hours after v1.23 shipped, `ListsView 2.swift` and `PracticeView 2.swift`
  materialised in `Sources/NihongoRideApp/` carrying their original July 29 mtimes, and
  `swift build` went red with `invalid redeclaration`. The working tree had been clean
  minutes earlier. `.gitignore` is no defence — git ignoring a file does not stop SPM
  compiling it — and neither is `git status` alone, since these arrive untracked. The same
  mechanism produced the seven `NihongoRide N.xcodeproj` copies at the repo root, which are
  harmless only because `*.xcodeproj/` is generated and ignored. If a build fails with
  redeclarations nobody wrote, look for a file with a space and a digit before `.swift`
  before looking anywhere else.

- **A null result from an uncalibrated checker is worthless.** Five near-misses in one session:
  an honesty judge reporting 205/205 that found 1 of 3 known-bad; a card check reporting "9
  flagged, 0 confirmed" because `v && v.flag` turned a missing agent result into a pass; a
  Chinese false-friend sweep finding 3 because it compared Japanese shinjitai to Simplified
  characters. Build the negative control before believing the number.
- **A gate and the thing it gates can share a blind spot.** Sudachi as the reading arbiter
  agreed with the generator's wrong reading 14 times out of 17 — both regress to the common
  reading, which is the failure under examination.
- **One rule written twice will drift.** Three times the Swift test and the Python gate
  disagreed and the Swift copy was the stale one: a fullwidth ？ outside its punctuation set,
  -ずる verbs conjugating on a じ stem, and the i-adjective POS tag written three ways across
  nine entries (recorded here as "nine different spellings", which was the count of entries,
  not of spellings — v1.21 §D collapsed the whole 42-tag vocabulary and put a data test on it).
- **A pipeline that reports "not installed" may be measuring the wrong interpreter.** The
  v1.26 handoff recorded that no python on this machine had `sudachipy`, measured correctly on
  `/usr/bin/python3`, homebrew's and anaconda's — none of which is the one the scripts use.
  `check_dictation_readings.py:338` exits with *"run with ./.venv-jp/bin/python"*, and
  `.venv-jp` had SudachiPy 0.6.11 installed the whole time. It is gitignored, so `git status`
  and casual listings hide it. Three real measurements on the wrong population, which nearly
  deferred a corpus correction for a reason that was not true. Grep the tool's own source for
  how it says to invoke itself before believing it is unavailable.

- **A pipe replaces the exit code of the command before it.** `xcodebuild test … | tail -60`
  reported **exit 0 for a FAILED suite** during v1.26, on the gate that decides whether a
  release ships. `xcodebuild` returns 65 on failure — calibrated, not assumed. This is the same
  shape as the `&&`-swallows-the-first-failure trap above, and it will keep arriving in new
  costumes: any status a script reads must come from the process that produced it.

- **A serialiser that does not round-trip will rewrite the whole file.** v1.26's first corpus
  edit used `json.dumps(indent=2)` against files written with `indent=1`, and reformatted all
  178,868 lines of `n1.json` for a three-token change. A diff that large cannot be reviewed,
  which is the same as not being guarded. Assert that re-serialising the parsed file reproduces
  it BYTE FOR BYTE before writing anything.

- **A unit test on a predicate is not a test of the screen that uses it.** v1.26 fixed two
  count-vs-run defects at the model seam, proved the fix by mutation, and then restored the
  ORIGINAL labels in `MenuView` — and all 527 tests stayed green. The tests held the predicate;
  nothing bound the view to it. The durable answer was to stop giving the view a number at all:
  the label STRING is composed beside the queue it describes, so the call site cannot choose
  the wrong quantity because it is handed neither.

- **An XCUITest suite that cannot run is not a suite.** v1.26 isolated the iOS UI target
  (CloudKit off, every store redirected) because those tests finish a REAL run and could push a
  phantom ride into the owner's real CloudKit database. Making them isolated made them RUNNABLE
  — without it an unsigned build traps in `CKContainer.init` and dies before any UI — and the
  first honest run found a case that had been failing for releases: it asserted three segments
  on `segmentedControls.firstMatch`, which stopped being the mode picker when the mode selector
  grew to six modes and became a row of buttons. It had been reading the two-segment LANGUAGE
  picker. The failure had always looked like an environment problem because the app crashed
  first. Run them: `xcodebuild test -project NihongoRide.xcodeproj -scheme NihongoRideiOS
  -destination 'platform=iOS Simulator,name=iPhone 17 Pro' CODE_SIGNING_ALLOWED=NO`.

- **A default that names a file goes stale silently, and a checker reading the wrong file
  reports "clean" exactly like a working one.** `check_versions.py` defaulted
  `--submit-script` to `scripts/submit_1_26.py`. Run bare during the v1.27 release it compared
  the project's build numbers against a release that had already shipped, and said FAIL for the
  right reason by luck. It now resolves the highest-versioned `submit_*.py` on disk and PRINTS
  which file it read, because "which input did you use" is the one fact a pass/fail line never
  carries.

- **STATE said archives are kept per release. Nothing keeps them.** This file recorded that
  `--upload` preserves each release under
  `~/Library/Application Support/NihongoRide-Archives/<version>-<sha>/` with a `BUILT-FROM.txt`.
  Neither `build-appstore.sh` nor `build-appstore-ios.sh` contains that logic; the directory
  holds two hand-made 1.24 folders and nothing since. The uploaded archive lives only in the
  run's temp directory, so **the path to gate must be read out of that run's own log** — which
  is what v1.27 did. A doc asserting a property nothing enforces, in the file that names that
  defect as the project's cheapest detector.

- **Seed a store with the store's OWN writer, never a hand-rolled encoder.** `RideJournal.save`
  and `.loadReporting` use `.iso8601` dates; a plain `JSONEncoder()` emits numeric timestamps,
  and `LossyLoad` then drops every row individually — so the seed loads as an EMPTY journal and
  every assertion built on it passes for the wrong reason. Caught only because the helper
  asserted its own seed had loaded. The existing `seeded()` helper hand-rolls an encoder for the
  review stores and gets away with it; that is a property of those stores' coding strategy, not
  a pattern to copy.

- **`SKStoreReviewController` is deprecated in its entirety** — `ios(10.3, 18.0)`,
  `macos(10.14, 15.0)` in the MacOSX26.5 SDK. `@Environment(\.requestReview)` replaces it and is
  available from **iOS 16 / macOS 13**, below this app's targets. Check the SDK's own
  `.swiftinterface` / headers before writing a StoreKit call; the plan that specified this
  feature named the deprecated API.

- **Apple's Analytics reports may not exist at all at this traffic level, and "not yet" looks
  identical to "never".** Requested 2026-08-26 (both `ONE_TIME_SNAPSHOT` and `ONGOING`, the
  first ever made for this app): **all 156 reports on both requests have zero instances** — no
  file generated, as distinct from a file reporting zero. Apple documents up to 48 hours for a
  first snapshot AND applies a privacy threshold, so the two explanations are separated only by
  waiting. Everything §G of the product plan nominates as a rollout guardrail — retention,
  sessions, active devices, deletions — currently has nothing behind it. Census download counts
  come from Sales and Trends instead (`scripts/sales_report.py`), which is a different API with
  different semantics: **Analytics is opt-in sampled and can report zero while real downloads
  exist; Sales and Trends is the census.**

- **Calibrating on one corpus does not mean the rule holds on another.** The
  translation-agreement check looked clean on 3,812 shipped sentences and was wrong four times
  out of five on the first new batch. Its number-comparison half was eventually **deleted** —
  one real catch against eight false positives over seven attempts to fix it.
