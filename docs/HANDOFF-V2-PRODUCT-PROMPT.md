## 三条硬约束,动手前先记住

1. **Stage 0 是分发,不是付费墙。** 这个 app 上架至今**只收到过一条评论**。一条评论是「流量接近零」的**测量**,不是「产品不行」的证据——但它意味着**在没有街的地方开店,装修得再好也赚不到钱**。初稿花了整篇讲 StoreKit 失败模式,完全没提分发,两家评审都指出了这一点。先做 ASO、评价引导、基线记录。
2. **Stage 1 是打赏,不是 Pro。** 那条唯一的评论说的是:**「非常完美」+「怎么收费找不到路口」+「希望有一次性」**。用户夸的是**免费版**,要的是**给钱的入口**,没要功能。初稿从「怎么付钱」推导出一整个 Pro 层——Gemini 3.1 Pro 把这个读法拆掉了。打赏罐的工程量是 Pro 层的零头,而且它回答的正是 Pro 层依赖的那个问题:**这个开发者到底有没有人愿意付钱。**
3. **没有任何一个已安装用户可以失去任何东西。** 用代码保证,不是靠冻结免费层。`AppTransaction.originalAppVersion` 能在**设备本地、无账号、无服务器、无追踪**的前提下认出老用户——我在出厂 SDK 里核实过了,`originalAppVersion` 和 `originalPurchaseDate` 都在,可用版本 macOS 13 / iOS 16,低于本 app 的 14.0 / 17.0。
   **⚠️ 但有一条没核实,它是设计闸门不是细节**:`AppTransaction.shared` 在没缓存时可能需要联网。一个卖点是「完全离线」的 app,老用户在飞机上打开必须不能掉权限。

   **失败规则(Codex 修正了计划自身的矛盾——§C 写「fail closed」而 §E 写「fail open」):绝不能因为一次失败,收回一个此前已经验证过的权限。** 把最后一次验证到的权限持久化并在离线时照常认账;只有在**从未建立过权限**的情况下才 fail closed;联网恢复后再对账退款和撤销。缓存一个 Bool 不算权限设计。

4. **不要为「用户拿回自己的数据」收费。** 这条是 Codex 在修订稿里抓出来的自相矛盾:这个 app 卖的就是「你的数据是你的」,再对导出收费,两件事不能同时成立。**纯 CSV 备份/导出免费**;要收费只能收在**加工过的工作流**上(Anki 模板打包、批量牌组管理、自动化)。

## 这个项目最贵的一条方法论,它在产品阶段依然成立

> **一个报「没发现问题」的检查器,在它被证明能对已知阳性样本报警之前,和一个坏掉的检查器无法区分。**

产品版的翻译是:**一个发布之后没法知道它为什么失败的功能,教不了你任何东西。**

具体到这一阶段,有五条已经踩过的:

1. **「只用 App Store Connect 衡量」是把失明合理化。** ASC 能告诉你转化率,但不能告诉你**是没人看见还是看见了不买**——两个相反的问题,修法也相反。三家都驳回了,而且给了同一个区分:**Data Not Collected 禁止的是「收集」,不是「计数」**。本地、不上传、不可识别的计数器不是追踪,也不改变隐私声明。
2. **而且初稿连基线指标都选错了。** Apple 那个叫 "Conversion Rate" 的指标是 **下载数 ÷ 曝光数**,是**获客**指标,结构上就没法给「免费转付费」做基线。要用 **Download-to-Paid cohorts** 和 proceeds-per-download。
3. **「参与度没法测」是**事实错误**。** Apple 自己就报留存、会话、活跃设备、卸载,不需要任何 SDK,也不改隐私标签。前两稿断言了一个并不存在的失明,还为它写了一套辩护。它测不了「哪个模式被用」,但能回答**「变现有没有伤害整体使用」**——那才是该叫停发布的问题。
4. **要求可证伪却不写阈值,等于任何结果都能被合理化。** 而且阈值要有统计:**100 次曝光零购买,在 95% 置信度下只能排除「转化率高于约 3%」;没有曝光计数的零购买,什么都排除不了。** §G 现在把样本量、观察窗、退款上限、留存护栏都写在写代码之前。
5. **按「架构上便宜」排功能优先级是供给侧偏见。** 初稿这么排了,还明说了。三家各自独立地把同两项对调(自定义素材**上移**,更多内容**下移**)。**三个评审用不同理由做出同一个对调,那本身就是结论。**

还有两条经济学上的硬约束:

- **一次性定价只能买「已经完成的东西」**(Gemini 3.1 Pro 抓出的初稿内部矛盾)。初稿一边说「订阅没有可租的东西」所以拒绝订阅,一边把「持续产出内容」当成 Pro 主打——不能同时成立。软件工具是诚实的一次性商品;**持续内容不是**,要卖就按离散有限包卖。
- **定价不是「回头再说」的事**(Codex)。价格决定预期、转化和盈亏平衡,所以**在写 StoreKit 之前**要先把 `新增下载 × 付费转化 × 净收入 − 内容与支持成本` 这个式子算出来,并且说清两个数:**多少月收入才值得做**、**为了搞清楚这件事最多愿意花多少工时**。这两个数只能你来定,agent 不许自己编。
  顺带:初稿写的价格区间 "¥30–90" 是有歧义的——按人民币讲得通,按日元荒谬。**明确写 CNY**,分地区定价,并且把付费墙和 IAP 元数据本地化成简体中文:唯一那条评论来自中国,而中国区目前既没有本地化的商品页,也没有能用中文回复的支持渠道。

## 什么时候算做完

这一阶段**没有**「全绿就能发」那种终点,因为大部分问题是决定不是验证。但有几条是硬的:

- **Stage 0 的基线必须在任何东西上线之前记录。** 没有基线,上线后第一个月的数字读不出任何含义——这就是这个项目关于「仪器」的规矩,原样适用。
- **kill criteria 必须写在写代码之前**,不是结果出来之后。
- **购买流程没被证明会失败,就等于没测过。** 离线路径、没登录 App Store 账号的路径、恢复购买的路径,三条都要测,当成闸门测。
- **老用户掉权限是这个产品扛不住的那种一星评论。** 失败必须**向「有权限」倾斜**。
- 涉及代码的部分,`swift test` 全绿 + 每个新测试被证明会红,这条不变。
- 发布前的对抗性评审跑过,阻塞项修完。
